# Architecture Decision Records

Phase-0 artifact (F-22). ADRs capture the *load-bearing* architectural decisions — the
ones that are expensive to reverse and that a reviewer or new contributor would otherwise
have to reverse-engineer from the code. Each record is immutable once **Accepted**: to
change a decision, add a new ADR that **supersedes** the old one (don't edit history).

Format: [0000-template.md](0000-template.md) (a trimmed MADR). Decisions that predate this
register were reconstructed from the codebase, the evaluation findings register, and the
`D-1`/`D-2` decisions logged there.

**0017–0021 are one decision in five records.** They reorient the tenancy model on a single
principle — *the provider holds less and reaches less* — and each supersedes a different part
of what came before. Read [0017](0017-provider-authority-is-delegated.md) first; the other four
follow from it.

The gateway's half of ADR-0013's old provider-plane trust (`grants.py`, the second-issuer/entitlement/ceiling machinery in `oidc.py`) was already removed wholesale in `ece1c75` — none of ADR-0017's replacement exists yet; the BFF's half (`grants.py`'s act-on-tenant/elevated-grant flow, `routers/provider.py`) is still live but already partially vestigial, since the gateway has nothing left to honor an elevated grant claim against. Slice 2 built: `CompositeAuthenticator` (`rbac.py`) gains a third, last-resort path — a bearer that fails both the JWT and static-key checks and starts with the `sgr_` prefix (a cheap shape check, so an invalid credential of any other shape never pays for the extra store round-trip) is checked live against `SupportGrantStore`; a valid one resolves to a `Principal` whose `subject` is the provider operator's own identity — never the tenant admin who approved it, never a shared "support" placeholder, the property ADR-0017 §7 names as needing testing rather than asserting, proven end-to-end in `test_support_grant_authentication.py`. Revoking a grant refuses the very next request — proven live, not inferred. Slice 3 built: Tier 1, sender-constrained proof-of-possession. A new pure module, `device_mcp_gateway/support_grant_pop.py` — Ed25519 only, no algorithm negotiation — verifies a signature over `METHOD\npath+query\ntimestamp`. An operator opts in by submitting `public_key` at raise time; the resulting grant is bound to it. **No nonce cache**: replay is closed by requiring each signed timestamp to be strictly newer than the last one a grant accepted (`SupportGrantStore.check_proof`, a new method, mutates the grant — unlike the plain liveness `check` — the one exception to "nothing but `revoke` mutates a live grant"), plus a bounded clock-skew window (`support_requests.proof_window_seconds`, default 30s). `CompositeAuthenticator`'s support-grant path now branches: `bound_public_key is None` stays exactly Tier 0; set, it additionally requires `X-Support-Timestamp`/`X-Support-Signature` headers and refuses the request if either is missing, malformed, or invalid — never silently falling back to bearer-only behavior for a grant that opted into more. Proven end-to-end (`test_support_grant_pop_authentication.py`): a signature over one path does not authenticate a request for another, a captured signature cannot be replayed, and a later signed request still succeeds after an earlier one. Slice 4 built: revocation interrupts in-flight work (§8). **A scope call flagged rather than silently narrowed**: `docs/kubernetes-architecture.md` confirms the gateway API tier itself is horizontally scaled in distributed mode ("stateless gateway replicas... `kubectl scale deployment device-mcp-gateway --replicas=3`"), so a `revoke()` landing on a different replica than the one running the call cannot reach it directly by any in-process mechanism. This codebase's own precedent for genuine cross-replica signaling (`shared/session_router.py`'s `SessionRouter`) uses a durable Redis Stream rather than pub/sub specifically because a fire-and-forget publish can be missed by a replica that is mid-restart — building the equivalent for revocation was judged not worth it here, because the case it would improve is already bounded: a call on a different replica still stops on its own (the F6 timeout watcher, or refusal on its very next request, since `check`/`check_proof` are live per-request already), just not the instant the revoke lands. New `device_mcp_gateway/support_grant_inflight.py` — `InFlightSupportGrantCalls`, a per-process registry of `grant_id -> {asyncio.Task}` — and a new router-level dependency, `rbac.track_support_grant_inflight`, ordered after `authenticate_request` in `main.py`'s `protected` router: while a support-grant-authenticated request executes, its task is registered; on cancellation, an audit event (`support_grant.call_interrupted`) fires before re-raising. `revoke_support_grant` calls `cancel_all(grant_id)` after a successful revoke and folds the interrupted-call count into the existing `support_grant.revoke` audit record rather than the response body, so the route's 204-no-content contract is unchanged. Proven end-to-end (`test_support_grant_inflight_authentication.py`, against the real `create_app()` wiring via `httpx.ASGITransport`): a slow in-flight call under a grant is cancelled the moment that grant is revoked on the same process (observed as `RuntimeError: No response returned.` — the task never reached `send`), and a fast, uncancelled support-grant call is unaffected by the new dependency. Slice 5 built: audit trail + the break-glass tenant-notification gap. New `device_mcp_gateway/tenant_notifications.py` — a durable, capped (`LTRIM`, not TTL'd) list a future tenant console will poll, not an email/webhook channel (the gateway has none); new route `GET /v1/notifications`, gated by a new scope, `notifications:read` (a standing bundle member alongside `support:administer`, but deliberately separate — reading it is passive visibility, not administering the support mechanism). Two producers write to it. Second, the one path that is equally silent by construction — a standing-consent self-issue, which has no per-instance human review — gets its own small tracker, `support_grants.SelfIssueActivityTracker` (a sliding trailing-window counter, deliberately a separate small implementation from `breakglass.BreakGlassActivity` rather than a forced shared abstraction, so its Redis key never shares a namespace with a real break-glass credential's subject); crossing the threshold (default 3 per 30 days, same defaults as break-glass's own) fires `support_grant.standing_consent.frequent_self_issue` and writes a notification. 2026-08-20 but only reached the records on 2026-08-21 — the acceptance commit moved the status

plan-digest window was read as unanswered while assessing build item 4, and the assessment
